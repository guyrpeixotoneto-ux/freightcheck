---
name: Production startup must migrate — Publish does not own the journal
description: DB_MIGRATE_ON_BOOT must stay "1" in production; Replit Publish's schema diff is not a substitute for the application's own migration runner.
---

**This note used to recommend the opposite, and that recommendation caused a real incident.** Do not disable `DB_MIGRATE_ON_BOOT` in production as a workaround for a readiness problem, and do not treat Replit Publish's schema diff as an alternative source of truth for which migrations are applied.

**Why the old guidance was wrong.** Publish's Development→Production schema diff can apply structural DDL, but it never writes to the application's own migration registry (`drizzle.__drizzle_migrations`). Every read of "which migrations are applied" in this codebase — `/api/readyz`, the readiness gate, `diagnosticar(observarBanco())` — is authoritative from that registry, not from inspecting the schema. Disabling `DB_MIGRATE_ON_BOOT` does not shift schema ownership to Publish in a way the rest of the system can see; it just makes the application's own convergence path permanently a no-op. With the key off, every production restart calls the startup sequence, `deveMigrarNaPartida()` unconditionally returns `false`, and the migration runner (`migrarComReparo`) is never invoked — no advisory lock, no journal write, no repair, ever. The database can stay behind the deployed build indefinitely, through any number of clean restarts, while the readiness gate correctly keeps rejecting product traffic the whole time because nothing is trying to close the gap. That is exactly what happened: `DB_MIGRATE_ON_BOOT` was set to `"0"` on 2026-08-22 13:16 UTC, and production stayed at 56/58 migrations — `0056_frota_promax` and `0057_total_do_pagamation` never applied — for the next three days, surviving multiple restarts, until this was diagnosed and reverted.

**The readiness incident this note originally reacted to was real, and it has a different, already-shipped fix.** The failure was migration work interfering with the startup probe during boot. The actual fix — shipped the same day, ~9.5 hours after the key was disabled — is architectural, not a disabled flag: `app.listen()` binds the port first; migrations run afterward, in the background; the startup probe target (`/api/healthz`) is pure liveness and never touches the database; and a separate readiness gate (`middlewares/portao-de-prontidao.ts`, `/api/readyz`) rejects product traffic — never the probe — until the migration queue converges. With that split in place, a slow or failing migration cannot fail the startup probe. Disabling `DB_MIGRATE_ON_BOOT` stopped being necessary the moment that fix landed, and staying disabled afterward only produced the outage above.

**How to apply:** Keep `DB_MIGRATE_ON_BOOT="1"` in the production artifact. If a future readiness incident looks similar, fix it in the readiness/startup-sequencing layer (`lib/prontidao.ts`, `lib/partida.ts`, the gate middleware) — never by turning off the application's own migration runner. See `docs/MIGRATIONS.md` for the full architecture and incident history.
